1. Purpose and scope

The program collects the draft of every professional Arena of Valor game (RoV in Thailand, league RPL) played by one team, and turns it into scouting statistics: what the team picks first, what it bans, what opponents ban against it, how it answers a given opponent pick, and how it manages its hero pool across a series.

The first focus team is Full Sense (FS). The data model is team-neutral. Focus is only a filter in the dashboard. Every Full Sense game contains the opponent's full draft as well, so when a second team is added later, its games against Full Sense are already in the database and count immediately. Until that team's other games are entered, its statistics describe only how it plays against Full Sense, and the dashboard must show the number of games behind every team-level number so this partial view is visible.

The input is images of the broadcast, supplied by the user. Automatic frame capture from VODs is postponed. Recognition of heroes from the images is postponed as well; version one is manual entry through a form that validates the draft.

The previous project in this repository, a minimap position tracker, was removed on 24 September 2026 and remains in git history only.

2. Facts about RPL that shape the design

  • Season size. RPL 2026 Winter has 9 teams, double round robin, every match best of five. The top four play a double-elimination bracket of best-of-seven series. A season is roughly 230 to 390 games. Full Sense alone plays about 16 regular-season series, so 50 to 80 games.
  • Global Ban-Pick. Applies to every RPL match. A team cannot pick a hero it has already used earlier in the same series. It may pick heroes the opponent used. In a best of seven, game seven returns to a normal draft. This makes series-level questions ("what do they save for game three") more valuable than single-game questions.
  • Side selection. The administrative home team chooses the side in game one. After that, the loser of the previous game chooses. The record must store who chose the side, not only who was blue.
  • Swap phase. After the last pick, teammates may trade heroes. The hero shown under a player name on the draft bar before the swap is often not the hero that player ends up playing. Two frames of the same draft on the FS versus SLX VOD showed different assignments, which confirms this.
  • Patches. The Thai server is patched every two to four weeks, so two to four patches fall inside one season. Every game must carry its patch, otherwise pooling across a season mixes different metas.
  • Heroes. About 128 to 130 heroes exist. Flowborn has five forms that are banned separately but count as one hero when picked, so the hero list needs a form field.
  • Liquipedia gap. Liquipedia records five picks per team in lane order and four bans, but not the interleaved pick order. Pick order is exactly what response-pick statistics need. Reading the broadcast is the only way to get it, which is the unique value of this project.

3. Legal position of the data

The original worry was that using Liquipedia or similar sites would be illegal. The research found the position is softer than that.

  • Liquipedia text is licensed CC-BY-SA 3.0. Using its tables with attribution is permitted. Its API has strict rate limits: one page-parse call every 30 seconds and a User-Agent with contact details. A research agent broke this limit on 24 September 2026 and this machine's IP was temporarily blocked, so any future use must respect the limits.
  • Facts are not copyrightable. Thai Copyright Act B.E. 2537 section 7 excludes facts having the character of mere information. The US cases Feist and NBA v. Motorola reach the same result for game data extracted from broadcasts. Extracting who picked what from a screenshot is therefore not the problem.
  • The real risks are redistributing the screenshots themselves and the hero icons, which belong to Garena and Tencent, and the terms of the platform the video came from. The design answer is that images stay on the user's PC and only extracted facts go to the cloud.

4. The two programs

The work is split into a local extractor and a cloud dashboard. The reason is not cloud compute, which was never the bottleneck. The reasons are that Python and OpenCV never have to run on a serverless host, and the screenshots never leave the PC, which removes both the storage problem and the copyright question.

4.1 Extractor (local, Python)

  • Input per game: the pre-swap draft bar screenshot and the post-game stats screenshot, plus three values typed once per series because the images lack them: date, patch, and which team was the home team in game one.
  • A review form ordered by the pick sequence, so the user enters B1, R1, R2 and so on rather than reading slots. This is the step that produces correct pick order.
  • Validation before save: four bans and five picks per side, no hero twice in a game, no hero repeated by the same team within a series except in game seven.
  • Output per game: one JSON file on disk, then a mutation that writes the same record to Convex. The JSON files are the backup and the source of truth; the Convex free plan has no daily backups, and the files allow rebuilding the database if the schema changes.
  • Later: recognition proposes values and the form only confirms them. The research recommends fixed slot crops, a DINOv2 or similar embedding nearest-neighbour lookup, and a pixel correlation check, with anything below a confidence threshold sent to the form. A vision language model is a fallback for text, not the main path. Every confirmed crop becomes a new reference image.

4.2 Dashboard (TanStack Start, Convex)

  • Read-only over confirmed data. No editing in the browser, so unverified guesses never reach the statistics and images never need uploading.
  • Statistics computed in Convex queries, or precomputed by the extractor at write time if query volume matters.
  • Focus team selector, defaulting to Full Sense, and a games-entered count next to every team-level number.

4.3 Keeping the halves in step

  • One shared schema. The extractor emits a JSON shape and a Convex validator mirrors it. Drift would make the dashboard silently show wrong numbers.
  • One canonical hero and team list, kept as a file in the repository that the extractor reads and a Convex table the dashboard seeds from.

5. Input images and what each one gives

5.1 Draft bar (pre-swap)

The RPL broadcast keeps a bar along the bottom of the screen during the draft. It persists across camera cuts, which is why a single screenshot is enough.

  • Caption line with team short names, stage, game number and series length, for example "REGULAR SEASON : FS VS BRU : GAME 1 [BO5]". The left team is blue side.
  • Four bans per side as grey icons, five picks per side as splash art, and the player name under each pick.
  • Working assumption to verify on a VOD: the five pick slots fill in that team's pick order. If true, the full 18-action sequence can be rebuilt from one frame, because the alternation between teams is fixed by the rules.
  • Missing: patch, date, and whether the ban slots are in ban order.

5.2 Post-game stats screen

  • Result for each team, series score after the game, game duration.
  • The final hero for each player. This is the post-swap mapping to store for player pools.
  • Per player: kills, deaths, assists, six items, damage dealt, damage taken.
  • Team totals: kills, gold, towers, dragons, slayers.
  • Bans repeated at the top, which serves as a cross-check against the draft bar.
  • Items are hard to read reliably from a screenshot and are optional in version one.

6. Data model

The core is a table of draft actions, one row per ban or pick in sequence. Every statistic derives from it. The remaining tables give context.

tournament(id, name, season, dateStart, dateEnd)
team(id, name, short)
player(id, ign, teamId, lane)
hero(id, name, forms[])              -- Flowborn forms
series(id, tournamentId, stage, bestOf,
       teamAId, teamBId, homeTeamId, date,
       winnerTeamId, rules = 'global_bp')
game(id, seriesId, gameNo, patch,
     blueTeamId, redTeamId,
     sideChooserTeamId, firstPickTeamId,
     winnerTeamId, durationS,
     tournamentId)                     -- denormalised
draftAction(gameId, seq 1..18, phase,
     teamId, side, action ban|pick,
     heroId, form?, playerId?, lane?,
     tournamentId)                     -- denormalised
playerGameStat(gameId, playerId, teamId,
     heroId, kills, deaths, assists,
     dmgDealt, dmgTaken, items[]?)
teamGameStat(gameId, teamId, kills, gold,
     towers, dragons, slayers)
  • seq on draft actions makes response picks, pick windows, first-phase pairs and last-pick analysis possible.
  • gameNo and sideChooserTeamId together with the series result make series analysis possible, including what a team does in the game after a loss.
  • playerId and lane on picks come from the post-game screen, not the pre-swap draft bar.
  • Global Ban-Pick locks are derived, not stored: the heroes a team used in earlier games of the same series.
  • Tournament and team ids are copied onto draft actions so statistics queries hit one table with one index, which matters in Convex where there are no joins.

7. Draft sequence and validation rules

The sequence below comes from Garena Vietnam's league rules and a Thai RPL broadcast overlay tool. No official RPL rulebook stating it was found, so confirm it against one VOD before hard-coding.

SeqPhaseSideAction
1 to 4Ban 1B, R, B, Rone ban each
5Pick 1BlueB1
6, 7Pick 1RedR1, R2
8, 9Pick 1BlueB2, B3
10Pick 1RedR3
11 to 14Ban 2R, B, R, Bone ban each
15Pick 2RedR4
16, 17Pick 2BlueB4, B5
18Pick 2RedR5

Validation rules applied before a game can be saved:

  • ☐ Exactly four bans and five picks per side, 18 actions in total.
  • ☐ No hero appears twice in one game, counting bans and picks together.
  • ☐ No team picks a hero it picked in an earlier game of the same series, unless the game is game seven.
  • ☐ Every pick has a player and the five players of a team are distinct.
  • ☐ The bans on the post-game screen match the bans on the draft bar.
  • ☐ Patch and date are set, and the date lies inside the tournament.

8. Statistics for the dashboard

With 50 to 80 games for the focus team, many cells will hold one to three games. Every number is shown with its count. Conditional statistics are shown as counts, and are ranked only when the count is at least three. No percentages are shown under a count of three.

8.1 Version one

  • Draft priority. What the team takes with first pick on blue, what it takes with the R1 and R2 pair on red, and what it leaves for last pick.
  • Bans. What the team bans, split by ban phase, and what opponents ban against it, attributed to the player the ban targets.
  • Response picks. After an opponent hero appears, what the team picks in its next pick turn. The window is the team's next turn, not the rest of the draft.
  • Player pools. Heroes per player with games, wins and last played date, plus the heroes still available later in a series under Global Ban-Pick.
  • Series view. Game by game: side, who chose it, picks, bans and result. This is the page a coach reads before a match.
  • Game table. Results and team totals per game, so drafts can be linked to what happened.
  • Presence. Picks plus bans over games for each hero, filterable by patch and opponent.

8.2 Later

  • Lane pick-order priority, the average pick slot per lane.
  • Flex picks: the same hero played in more than one lane by the team.
  • Side preference when the team has the choice, and win rate by side.
  • Win rates with Wilson intervals or shrinkage toward the league rate.
  • Draft prediction from frequencies or association rules, only once several seasons exist.
  • Items, damage-based statistics.

9. Storage and hosting

Convex is the database. It fits the user's stack preference and the data volume, and the free plan covers the project.

Convex free limitThis project, one season
Database storage 0.5 GBAbout 15,000 small rows, a few MB
Function calls 1M per monthA few thousand
Database I/O 1 GB per monthA full-season scan is about 3 MB; precompute aggregates if the dashboard reruns many queries
Per-query scan 32,000 documentsOne season fits; filter by tournament for several seasons
File storage 1 GBNot used; images stay local

Consequences of the free plan: one developer, no daily backups, and writes fail rather than bill when a limit is exceeded. The JSON files written by the extractor are the backup.

Hosting is a preference because TanStack Start's server adapter hides the platform. Pick one host, not all three. Cloudflare has the most generous free tier and pairs with R2 storage if images ever need to be hosted. Vercel has the least setup and the smoothest previews, and its free plan is non-commercial only. Netlify offers nothing extra here. Since data entry and statistics live in Convex, the host only serves the frontend and the choice is cheap to reverse.

10. Build order

  1. ☐ Confirm on one VOD that draft-bar pick slots fill in pick order, and that the ban slots fill in ban order.
  2. ☐ Write the shared schema: JSON shape, Convex validators, canonical hero and team list.
  3. ☐ Build the extractor's manual entry form with the validation rules, writing JSON to disk and to Convex.
  4. ☐ Enter the Full Sense games played so far in RPL 2026 Winter.
  5. ☐ Build the dashboard pages in section 8.1, with the games-entered count on every team number.
  6. ☐ Deploy the dashboard to the chosen host.
  7. ☐ After 20 to 30 confirmed games, add image recognition to prefill the form, tuned against those games.
  8. ☐ Widen to a second team.

11. Open questions

  • ☐ Does the pre-swap draft bar really show picks in pick order? If not, the form must take the order from the user.
  • ☐ Should opponent player names and post-swap heroes be required from day one? Recommended yes, because they become the opponent's player pools later.
  • ☐ Which host: Cloudflare or Vercel.
  • ☐ Where the patch comes from for each game: the date mapped against a patch table kept in the repository, or typed per series.
  • ☐ Whether to also enter playoff series, which are best of seven and add the game-seven exception to the validation.
